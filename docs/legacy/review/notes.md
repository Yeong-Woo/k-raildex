# 구현 중 리뷰 메모 (라운드 파일로 옮기기 전 임시 기록)

형식: `- [Phase/작업] 내용 — 왜 리뷰가 필요한지`

- [Phase 0] Astro 7.3.8 + @astrojs/react 5.0.7 조합에서 빌드 시 Vite 8 deprecation 경고(`optimizeDeps.esbuildOptions`, `esbuild` → `oxc`)가 다수 출력됨. 기능 영향 없음. React 통합은 Phase 2 지도 탭 전까지 실제로 쓰지 않으므로 Phase 1 완료 시 제거 여부 검토 — 경고 소음 vs 나중 추가 비용
- [Phase 0] pnpm 12는 빌드 스크립트 승인을 `pnpm-workspace.yaml`의 `allowBuilds`로 받음(`onlyBuiltDependencies`는 무시됨). esbuild·sharp 허용 — 리뷰어가 공급망 관점에서 확인
- [Phase 0] `scripts/validate.ts`는 참조 무결성을 필드 이름 접두사로 추정(operator\_\* → operator 등). 새 참조 필드를 추가하면 이 매핑도 갱신해야 함 — 누락 위험
- [Phase 1 site] 기본/상세 모드(D2)를 "모드 전환 버튼" 대신 페이지마다 `<details class="advanced">` 하나로 구현하고, 열림 상태를 localStorage 에 기억해 모든 페이지에 적용 — 명시적 토글 UI 가 필요한지 리뷰어 판단 필요
- [Phase 1 site] 상태값 `closed` 라벨을 개체별로 구분(노선 폐선 / 역 폐역 / 운행 계통 운행 종료). `rapid`=쾌속, `express`=급행, `limited`=특급 으로 번역 — TERMINOLOGY.md 4절 "급행/완행/직통"과 대조 필요(rapid·limited 는 사전에 정의 없음)
- [Phase 1 site] 운행 계통 종류 `intercity` 를 "일반열차", `wide_area` 를 "광역전철"로 표기 — TERMINOLOGY 1절(광역철도 vs 광역전철)과 일치하는지 확인
- [Phase 1 site] 용어 페이지는 `docs/TERMINOLOGY.md` 를 Astro 마크다운 import 로 그대로 렌더링. 앵커는 Astro 기본 슬러거(예: `#4-노선과-운행-계통`)라 문서의 제목을 바꾸면 사이트 내 링크(노선 목록·운행 계통·열차 등급 페이지의 3개 앵커)가 깨짐 — 문서 편집 규칙에 적을지 검토
- [Phase 1 site] 역 상세 제목은 `name.ko` 에 "역"을 붙이되 이미 "역"으로 끝나면(공식 역명 "서울역") 붙이지 않음 — 규칙(data-conventions 4절)과 어긋나는 데이터가 들어오면 표기가 흔들릴 수 있음
- [Phase 1 site] 환승 표현은 두 겹: (1) 한 역이 여러 노선(`line_ids`/line-stations)에 속함, (2) 같은 `transfer_group` 의 별도 역. 역 상세 배지 "환승역 · N개 노선"은 둘을 합산 — ingest 병합 규칙이 확정되면 (2)가 거의 안 쓰일 수도 있음
- [Phase 1 site] 외부 지도 링크는 OpenStreetMap 만. `coord_source: osm` 좌표에 대한 ODbL 표기는 출처 페이지에만 있고 역 상세에는 "OpenStreetMap" 라벨만 — 라운드 3(라이선스)에서 충분한지 확인
- [Phase 1 site] 노선도 `embed` 모드 렌더링은 구현했으나 현재 `route-maps.yaml` 이 전부 `link` 라 실제 이미지로는 검증하지 못함. `public/route-maps/` 디렉터리도 아직 없음(데이터 담당이 파일을 넣을 때 생성)
- [Phase 1 site] `pnpm check` 를 위해 `@astrojs/check`, `@types/node` 를 devDependency 로 추가(후자는 `scripts/validate.ts` 의 `import.meta.dirname` 타입 오류 해소용). scripts/ 는 건드리지 않음
- [Phase 1 site] 역 목록은 전체 역을 한 페이지 표로 렌더링(JS 필터). 실제 데이터(1,000역 이상)에서 HTML 크기·초기 렌더가 문제되면 지역별 분할 검토
- [Phase 1 site] 색 대비는 수동으로 고른 값(본문 ≥7:1, 배지 ≥4.5:1 목표)이며 자동 측정(Lighthouse·axe)은 하지 않음. 노선 `color` 는 데이터 값 그대로 점(dot)과 왼쪽 테두리에만 쓰고 글자색으로는 쓰지 않음(대비 보장 불가)
- [Phase 1 site] 헤더 검색은 첫 포커스 때 `search-index.json` 전체를 내려받음. 전국 데이터 기준 수백 KB 예상 — 크기 확인 후 gzip 만으로 충분한지 판단
- [Phase 1 ingest] **병합 규칙 3b 추가**: RAFIS 역(좌표 없음)이 표준데이터의 같은 이름 클러스터 하나와만 대응하고 그 클러스터에 국가철도 운영기관(한국철도공사·공항철도·네오트랜스) 행이 있으면 자동 병합(236건, report.md "운영기관 규칙(3b)"). data-conventions.md 3절은 "좌표 없으면 수기 지시 없이는 병합하지 않음"이라 규칙에서 벗어남. 근거: RAFIS 는 국가철도 역 대장이고 표준데이터의 한국철도공사 행은 같은 국가철도 역. 안 받아들이면 `NATIONAL_RAIL_OPS` 를 비우면 되고, 그러면 산본·대야미 같은 광역전철 역 236개가 RAFIS/표준데이터 두 레코드로 갈라진다 — 규칙 문서 갱신 또는 롤백 결정 필요
- [Phase 1 ingest] 규칙 3b 에 공항철도·네오트랜스를 포함한 것은 "신분당선·공항철도는 국가철도(민자)"라는 운영자 판단. 표준데이터의 신분당선 운영기관명이 "경기도 신분당선"이라 operators.yaml 에서 op-neotrans 로 매핑한 것도 추정 — 확인 필요
- [Phase 1 ingest] 일반·고속철도의 **물리 노선을 만들지 못함**. RAFIS 에 노선 컬럼이 없고(기준역간KP 만), 코레일 "철도운영정보 노선정보"는 "경부경부3경원" 같은 운행경로 코드 2,146행이라 노선 목록이 아님. KTX 노선별 역정보의 노선명으로 `line-ktx-*` 7개만 만들었고 category 는 데이터셋 분류대로 high_speed 로 두었다(중앙선·중부내륙선·전라선·경전선 KTX 가 일반선 구간을 달리는지는 데이터 근거 없음). 경부선·호남선 등 철도거리표 기반 물리 노선은 PLAN 1-5 후속(HWP 파싱 또는 수기) — 모델 상 Line 이 "KTX 운행 노선"과 "물리 노선"을 섞게 되는 점 검토
- [Phase 1 ingest] 좌표 출처 두 개(국가철도공단 철도역 정보, 코레일 역 위치)가 서로 틀린 곳이 많다. 철도역 정보는 좌표가 한 행씩 밀린 구간(옥산→함창→점촌→용궁→개포 연쇄)과 0,0 행 12개, 코레일 역 위치는 소수 2자리 저정밀 행과 명백히 틀린 행(행신이 인천 앞바다, 나주가 서쪽 바다)이 있다. 둘 다 있을 때만 교차 검증(저정밀 제외 → 그래도 충돌이면 좌표 생략 29건). **한쪽만 있는 RAFIS 역 좌표는 검증되지 않았으므로** 지도 탭 전에 샘플 검수 필요

- [Phase 1 ingest] Station.name.ko 는 끝의 "역"을 항상 떼었다(서울역→서울, 광주송정역→광주송정; 원문은 aliases). data-conventions 4절의 "'서울역'이 공식 역명인 경우는 '서울역'" 과 다를 수 있음 — 표기 원칙 확정 필요

- [Phase 1 ingest] 운행 계통 시드(`data/own/services.yaml` 44건)의 `line_ids` 는 역 인접 관계로 자동 도출했다. 경의중앙선 서비스의 경원선(용산~청량리) 구간처럼 "순서미확인" 구간 때문에 빠진 노선이 있고, 4호선 서비스에 수인선(한대앞~오이도 공용 구간)이 빠지는 등 수기 보정이 필요. 서비스 이름("수도권 경의중앙", "수도권 공항")도 국토부 노선명 그대로라 다듬어야 함
