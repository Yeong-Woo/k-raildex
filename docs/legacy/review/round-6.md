### Q142. 진실 원천(source of truth)을 언제까지 git YAML 로 두는가?

- 배경: 지금은 data/own YAML 이 원천이고 빌드가 JSON 을 만든다. 쓰기 API 를 붙여도 변경 묶음 → git 커밋으로 반영하면 이력·되돌리기·재현성이 그대로 유지된다. DB 를 원천으로 바꾸면 동시 쓰기·대량 질의가 쉬워지지만, 이력은 DB 감사 테이블로 따로 만들어야 하고 YAML 은 내보내기가 된다.
- 선택지: A. 계속 git YAML 원천, DB 는 읽기용 투영(단계 C·D) / B. 쓰기 API(D 단계) 도입과 동시에 DB 원천으로 전환 / C. 데이터 규모·쓰기 빈도가 기준(예: 월 변경 묶음 수백 건)을 넘으면 전환
- 임시 가정: A(전환 판단은 C 의 기준으로 다시 묻기)
- 답변: B. 쓰기 API(D 단계) 도입과 동시에 DB 원천으로 전환 (2026-10-14, 대화로 답변)

- 선택지: A. 묶음마다 브랜치·PR 을 만들고 사람이 머지(CI 검증 후) / B. 승인 = 기본 브랜치 직접 커밋(CI 실패 시 자동 되돌림) / C. 하루 단위로 모아 PR 하나
- 임시 가정: A
- 답변: B. 승인 = 직접 반영(기본 브랜치 커밋 또는 DB 반영), CI 실패 시 자동 되돌림 (2026-10-14, 대화로 답변)

### Q145. API·DB·수집기를 어디서 돌리는가(호스팅)?

- 배경: 공개 사이트는 정적(GitHub Pages 계획, P1·P2)이라 서버가 필요 없다. 수집기·API·DB 는 상시 실행 환경이 필요하다. 비상업 원칙상 비용이 작아야 한다.
- 선택지: A. 지금 쓰는 Docker(docker-compose)를 운영자 서버 한 대에 — api·db·collector 서비스 추가 / B. 수집기만 GitHub Actions 예약 작업(cron)으로 돌려 PR 생성, API·DB 는 보류 / C. 관리형 클라우드(DB·컨테이너)
